Added, edited and removed entries are now each selected once, unchanged ones never, and the old values need not be copied. The owner applies the restart list only after the preferences have been saved successfully.

- **Extension boundary:** the [architecture](architecture.md#what-belongs-in-an-extension) now explains how a guest owns a feature and exports it to other clients, using the offline map to distinguish local computation from privileged host I/O. This describes existing capabilities; it introduces no new ABI, storage or permission.

## E-156 — Extension canvases: owner memory regression

Status: **fixed on desktop and in isolated Android tests; phone verification pending.** Extensions now render their own pixels in their own process (WASM `canvas`, Skia in the helper). After this landed on the workstation, the owner's memory rose from ~40–50 MiB to 142–290 MiB RSS once Location's canvas page had been opened, and stayed there after the page was closed (owner's observation, then smaps: ~242 MiB anonymous mappings in the owner, 0 live raster bytes after close in a reproduction; window ~46 MiB anonymous retained). The extension Monitor was checked by the owner and is not the cause (owner 49 → 49.2 MiB, then flat). No earlier Monitor growth incident is recorded in these logs.

Measured on the workstation before the fix, with ~22 MB frames (3392 × 1600), 30 wheel steps through the local page-event path: owner 510 ms CPU, window 370 ms, Location helper 430 ms. The cause: the owner relayed every full frame from helper to window, allocating a new raster per frame across its threads, and glibc kept the freed arena pages. Separately, helpers that never draw rose from ~5 to ~10–12 MiB RSS (PSS ~2 MiB: shared Skia pages). `scripts/memory-gate.py` is a manual, Linux-only acceptance check run on the workstation after a deployed build has started (it measures running processes, so it cannot run before installation); phones are measured separately with `dumpsys meminfo` PSS. A build that fails it is not kept as the accepted state.

**Fix (desktop):** the owner now only authorizes a direct helper → window frame stream with a one-use token and never reads pixels; the window enforces frame bounds, rate and the 64 MiB retention itself; two reusable buffers; `MALLOC_MMAP_THRESHOLD_=4194304` was set at window launch so frame-sized blocks return to the OS. Matched 30-input run at 3000 × 1500: owner CPU 2,270 → 60 ms; owner RSS after two open/close cycles 294.0 → 54.0 MiB with zero raster-sized allocations; window back to its fresh 68.5–69.6 MiB after closing (default allocator: 104.1 MiB). Helpers that never open a canvas run `peersus-wasm-host` without Skia (3.27 MB): RSS 9.27–9.45 → 4.08–4.41 MiB, PSS 1.76–1.86 → 1.01–1.06 MiB. On the workstation after deployment and restart, before opening a canvas: owner 42.2, window 101.7, light helpers ~6 MiB RSS.

**Fix (Android and GPU, in isolated tests):** Android shares the two-buffer pool (zero retained raster bytes after unmount); the compositor updates one texture per canvas in place and purges unlocked GPU resources on unmount; the window's Skia GPU budget is 64 MiB (was 256). Skia budgeted memory after unmount in a 30-raster test: OpenGL 6.32 → 0.29 MiB, Vulkan 6.04 MiB → 4 KiB. On the owner's phone before this fix: main process 219 MiB PSS after leaving the canvas, 94.5 MiB of it Graphics. The phone has not been re-measured with the fix.

## E-159 — Pointer at the edges, the wheel, and an extension that ran out of fuel

- **Wheel across an edge (observed by the owner with a real mouse, from one Linux desktop to another):** the capture now gathers what the desktop says for a scroll into whole notches at the end of each frame (`desktop_capture.rs`, `Wheel`): 120ths of a notch for a wheel, a distance for a smooth scroll, the notches kept when one frame says both. The receiving desktop keeps one input device open between batches (`desktop_input.rs`). The owner saw the wheel scroll up and down on the other desktop. On GNOME 51 a plain wheel arrives as whole ±120 steps. Why the wheel did not arrive before is **not established**; the smooth (touchpad) path was seen only with a synthetic touchpad (below), not with a hand.
- **A push is needed to cross (unit tests; one crossing observed with a synthetic mouse):** a pointer that touches an edge is taken but not carried over until it is pushed a further `EDGE_PRESSURE`; pulled back, slid along the edge, left still for 300 ms, or followed by a key, a button or the wheel, it is given back where it was (`input_follow.rs`, `Push`). In one run between two Linux desktops the push carried the pointer over 11 ms after the desktop stopped it, the other desktop got its first pointer event 4 ms later (the two clocks compared over one connection, ±2 ms; its input device was already open), and the way back returned the pointer. One run, on a busy machine; not yet observed with a hand.
- **Another barrier on the same edge (observed, cause read in source, not proven by removing it):** with a synthetic mouse on GNOME 51.1 the desktop said it took the pointer during the push against the left edge in one push of six; in the other five it said so only at the first step away from the edge (read from the desktop's own signals on the session bus). The desktop's barrier code picks one barrier when two lie on the same line and stops looking once a plain one has clamped the motion, so a capture barrier behind another one is reached only by motion the other lets through, or when it happens to be picked first. On the test desktop an enabled shell extension (Desktop Cube, edge workspace switching) keeps such barriers on the whole left and right edges. The portal accepts a capture barrier only on a screen edge, so the application cannot move its own. An earlier reading of the same trace as the desktop "bouncing" the pointer was wrong: the motion was the test's own way back.
- **Extension stopped by itself (observed, fixed in the extension):** the host now records how a helper ended (`service.rs`); it named `out-of-fuel` for the map extension. Reading one saved map tile in a single turn cost up to 38.9 M fuel against a limit of 50 M; bounded turns bring the most expensive turn to 16.7 M for the same twelve saved tiles, in the same number of turns.
- **Halo:** it turns twice and rests (`portal.rs`). In the builds on all four devices; the phone at rest is measured below, the halo turning is not.
- **The gated build, installed on four devices (observed with a synthetic mouse and by reading processes):** the strict gate passed on this tree (95 test binaries, 3,458 tests, the dependency audit) and the build was installed on both desktops and both phones. After it:
  - A wheel turned a quarter notch at a time arrived on the other desktop as whole notches: eight quarters down as two notches down, eight up as two up.
  - Two fingers moved 33 mm down a synthetic touchpad arrived as 33 notches one way, and back up as 33 the other way (the desktop says such a scroll as a distance; ten of its units are a notch, as the desktop itself counts a wheel's).
  - The other way round, notches sent by the other desktop's application were replayed here, four of four once this desktop's input device existed. When a notch was the very first input after this application started, that notch was lost (the device is made with the first input and the desktop needs a moment to find it); in a real crossing the pointer's position comes first.

## E-160 — The wheel of a device with a pointer of its own, and a map with nobody on it

- **The wheel scrolled the wrong place (cause observed, fix observed on the receiving desktop; not yet with the owner's hand):** a device with a pointer of its own is a pen on the receiving desktop, and a desktop gives a pen no wheel: the notch goes to the shared mouse and turns what is under the desktop's *own* pointer. A full-screen test window on the other desktop showed it: the pen moved over the middle of the screen, the notches arrived from the plain pointer, and that pointer stood at the left edge, where an earlier test of mine had left it. So the wheel "worked" whenever the desktop's own pointer happened to lie over the page, which is why it was seen working at noon and not in the evening. Probably the same cause as the wheel "not arriving" before E-159; that build is gone, so it stays unproven. The fix (`desktop_input.rs`, `Pen::under`): before a notch of such a device the desktop's own pointer is brought under its pointer, through the shared absolute pointer, said beside itself first so the system does not swallow a position it already had; that device is made with the pen so the desktop has found it by the first notch. On the installed build the same window received the plain pointer at the pen's place just before each notch (two places tried). One consequence, accepted: a person at the receiving computer sees its own pointer jump to the other pointer when that one scrolls.
- **Nobody on the map of a desktop (cause read from each device's state):** on one desktop Location held no permission for any device and none to read its own position; it already held none before the day's first update of the extension there (the deploy tool said `1 own, 0 device sets` before and after). On the other desktop the extension was not installed. The phones had both, which is why each saw the other. With the permissions given and the extension installed, both desktops listed the two phones' positions within the phones' next turn. A device shares when its extension starts and then every five minutes, and what arrives is kept in memory only: after a restart the map is empty until each device's next turn, which looks like devices appearing at random. That wait is gone: a device now asks, at its start and whenever nothing or only something old is known of a device, where that device is (a second exported service, `location.wanted`, under the same permission on both sides), and the device asked shares what it already knows. It never looks for itself sooner than its five minutes, and answers a question at most every thirty seconds. Measured on one desktop: its extension restarted, memory empty, both phones known again at the first look 2.1 s later, where before it took up to five minutes. The extension's earlier rule that nothing is asked of another device is ended by this, on the owner's word that a map must not wait.
- **One question was not enough (observed, then fixed and measured):** with the first form of asking, an update that restarted Location on all four devices left one desktop knowing both phones and the other knowing none for minutes: its single question came to nothing (which of the possible reasons, a device not yet taking a position from the asker or not yet knowing where it was, was not established), and the next one was five minutes away. A device asked that has not shared is now asked again after fifteen seconds, then after twice as long each time, in the end once per five minutes; the device asked keeps for a minute a question it cannot answer yet, and answers the device that asked, not every device, at most once per ten seconds for one device. Measured after the next such update: both desktops knew both phones 8 s after the last device was updated. What a device received is still kept in memory only: a device that is offline when the extension starts is not on the map until it is reachable, and an extension has no service to keep data of its own across a restart.
- **A listing that failed wiped what was known:** when the application could not answer a listing of the devices (late, busy), Location dropped every received position as if it had been refused. Only a refusal does that now (`lib.rs`, the listing answer); unit-tested with six hours and three kinds of failure. Whether this happened on a device is not known: no such failure was logged.
- **A desktop does not know where it is:** both desktops answer that location is off or not allowed to the application. The desktop's location service is on on one and off on the other; why the one that has it on still gets no position is not looked into.
- **Two devices on one desk were one marker:** markers that would cover one another are now drawn apart around the place they share, two side by side and more on a ring, a parted group kept inside the map, and a name kept clear of the other markers and their names (`canvas_scene.rs`, `spread`). What a marker is of does not move. Unit-tested; installed on four devices; not yet seen on a screen.
- **The submission's check did not start for Location:** two review threads on its pull request are unresolved, and the check refuses to build until they are. The other four submissions passed on their new commits.

## E-161 — 2026-11-22 · A canvas page shown again, where the programs live, and one command for GitHub
