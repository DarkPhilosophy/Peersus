# What the first-day website must contain

Purpose: a concrete review of `site/` as it exists on 2026-11-12 plus the exact changes required for launch day. Researched on 2026-11-12.
Owner decision (2026-11-17): the site is Peersus's own. LocalSend and AlterSend (and every other product in [competitors.md](competitors.md)) are research, not templates: no layout, section, wording or comparison page modelled on their sites. The site's look comes from the application itself (its drawn screens, the portal, its accent pairs).
Mechanics note: `site/build.py` stages a fixed allowlist (`FILES` plus registered generated assets) and validates local links, CSP meta, duplicate ids and the supporters JSON. New trust boundaries are deliberate: only the Architecture page is allowed to read the fixed public map publication on GitHub.

## 1. What exists today (verified by reading `site/`)

- `index.html` (as of 2026-11-17) — hero ("Your files. Your other device.", "Download the test build" leading to `install.html`), the phone tour: the application's own screens with a rail of seven cards (Send, Receive, Peers, Transfers, Extensions, and the Remote and Monitor extensions), status strip, *01 / The number* (pairing by a number both people read, drawn as the two screens show it), *02 / Around the app* (cards to Store, Download, Security, Support) and the disclaimer box. The store list moved to `store.html`, the Ko-fi block, the supporters list and the tips FAQ to `support.html`, the security section to `privacy.html`, a short FAQ ("Before you ask") to `install.html`. Strict CSP (`default-src 'self'`), `referrer: no-referrer`, skip-link, `lang`, colour-scheme meta. *(Done by `site/build.py`: canonical address, `og:` and `twitter:card` tags on every page, and a generated `robots.txt`, `sitemap.xml` and `llms.txt`; only an `og:image` is missing.)*
- `install.html` — build-from-source guide (accurate today; wrong audience for launch visitors). *(Since done: it is the download page, titled "Download — Peersus", listing the prerelease builds through `downloads.js` with the build guide below them; the home page's "Download the test build" leads there, and `#install` no longer carries the "no public release downloads" line.)*
- `privacy.html` — exists as a draft per [store-policy-google-play.md](../store-policy-google-play.md) C1; must be finished (developer name + contact) because Play **and** Apple 5.1.1(i) require a published privacy URL ([Play Help](https://support.google.com/googleplay/android-developer/answer/10144311), [Apple guidelines](https://developer.apple.com/app-store/review/guidelines/)).
- `architecture.html` — the five-view source map: overview, code, broker, file journey and delivery, with search, drill-downs and guided flows. The stage includes a snapshot. The browser caches the public map in IndexedDB and checks GitHub only when the page opens: at least 24 hours after a successful check, or one hour after a failed one. If the browser cannot save the check time, it may check once per opening. No analytics or visitor identifier is stored.
- `relay.html` — `noindex` page describing the project relay. Keep `noindex`.
- `app.js` — reveal-on-scroll (disabled under reduced motion), the shared theme toggle and in-place navigation on pages with the same policy. Architecture opens as its own document so its narrower, page-specific GitHub permission does not carry to other pages.
- `site/brand/` — `peersus.svg` and `peersus-light.svg` (icon on a dark or light plate), `peersus-mark.svg` and `peersus-mark-light.svg` (transparent mark for dark or light backgrounds), all generated by `crates/peersus-ui/assets/generate_icons.py`.
- `docs/assets/` — `readme-hero.png` (1672×941, real Android app preview, Romanian UI) + `readme-hero-bg.png`.

## 3. Copy corrections for launch day

- The hero line "Move it. Don't store it." is fine as a tagline; keep the existing sub-line that clarifies it's about the handoff, not that receiving devices/relays store nothing — [marketing.md](../marketing.md) already warns about this.
- *Done: the "no public release downloads linked here yet" line is gone; the hero's "Download the test build" leads to `install.html`, which lists the prerelease builds.*
- Ko-fi block stays on the website (external link, user's choice), but the *app's* About-page button is a store-policy risk on Play/Apple builds ([store-policy-apple.md](../store-policy-apple.md) 3.1.1, [docs/support.md](../support.md) notes Play compatibility unverified) — owner decision; don't promise "free of charge, forever" wording in app copy that store builds can't keep.
- Connection diagram: keep labelled as illustration (already done); never caption it "screenshot".

## 4. Install-steps detail (`install.html`)

- **Linux:** download tarball → checksum verify (`sha256sum -c`) → extract → run `peersus-ui`. Name the five programs the archive contains (per [app-update.md](../app-update.md)). State "release build; tested on the distributions in the engineering log" — do not list distro compatibility nobody verified.
- **Android:** APK download → "install unknown app" flow → what the community flavour contains (native extensions + Shizuku self-update path, per [app-update.md](../app-update.md) + store-policy F section) → Play flavour note ("Play version is being prepared; it will not include native extensions or the self-updater"). Never link the APK from r/androidapps (their rules allow only store/GitHub links — channels.md).
- **Both:** "where files arrive" (receiving folder), "how to unpair", "how to turn off relays", "where logs live" — the four questions every first-time user asks.

## 5. SEO (minimal, honest)

- `title`/`description` per page (already present pattern). Canonical URL: the site is served by the project relay under its own name, `https://peersus.axxa.dev` (the address the application already names as the project relay, `peersus-core::relay::PROJECT_RELAY_URL`), so `site/build.py` (`SITE_URL`) writes that into canonical links, `sitemap.xml`, `robots.txt` and `llms.txt`; internal links stay relative. A separate product domain later is one constant and the site tests.
- Keywords that are true: "file transfer", "send files linux android", "open source airdrop alternative", "end-to-end encrypted file transfer", "send files over the internet without cloud". Put them in headings/FAQ answers naturally — no keyword stuffing, no "best" claims.
- `robots.txt`: allow all except nothing to hide (relay.html self-excludes via meta).
- OG/Twitter card + descriptive `alt` on every image (partially present — audit all `<img>`).

## 6. Accessibility (mostly done — keep it)

Already good: skip-link, `lang`, `aria-label` on nav/buttons, reduced-motion honored, `color-scheme` meta, textContent-only injection. To verify before launch: keyboard tab order through the download cards, contrast of the orange/blue status cues in both themes, `alt` text on screenshots (describe what the screenshot *shows*, not "screenshot").

## 7. Analytics-free approach (a feature, not an absence)

No analytics, pixels, or outgoing referrer (`no-referrer` is already set). The Architecture page's check for the public map on GitHub is the only automatic third-party request. Our measures are GitHub release download counts and opt-in feedback. If the owner ever wants numbers: server-side log counting by the host, or nothing — never JS trackers on a privacy tool's site.

## 8. Store-readiness hooks (later but cheap now)

- `privacy.html` URL must be stable forever — Play Console and Apple metadata will point at it; changing it later is a re-review.
- An in-app "Privacy policy" link is still missing in the UI per store-policy docs — flag to the build side (not a website change, but the website must exist at a stable URL first).
- Play listing text will need: short description (80 chars), full description, screenshots (phone + 7"/10" tablet minimum norms — verify current Play listing requirements when the account exists).

## 9. Pre-flight checklist for the site (all must pass on D-1)

- [ ] `python3 site/build.py --output <dir>` clean; new files added to `FILES`.

- [ ] OG image renders in a card validator (unconfirmed which validators still work without login — test with a real post in a draft community first).
- [ ] Dark + light themes, reduced motion, keyboard only.
- [ ] privacy.html final text reviewed by the owner (it names the developer).
