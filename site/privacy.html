TRANSPARENCY / DRAFT FOR OWNER REVIEW

Less collection.

This is a technical privacy-policy draft for a pre-release project, not a claim of legal review or regulatory compliance. Before public launch, the owner must approve it, name the actual website host and privacy contact, and confirm the final distributed application’s behavior.

Security at a glance

Encrypted device to device

File-transfer payloads use end-to-end encrypted QUIC connections. Each device has its own key, and a connection is made to a key, not to an address. When a direct path is unavailable, an optional relay can carry traffic that is already encrypted between the two devices: by design it cannot read your files, but it can observe connection metadata. You can turn relays off in the settings. There is no Peersus server in this picture, and no account.

Not always offline. Not risk-free.

Connectivity depends on your network and configuration. Peersus has not received an independent security audit. Trust the devices you pair, keep backups, and verify important files after transfer.

Plugins are a separate decision

Clipboard integration is under development, with Android foreground-app restrictions. Optional cloud upload is also under development: a provider may store readable files. Neither is a promise of automatic background sync or encrypted cloud storage.

This static website

The website contains no advertising, analytics, tracking pixels, embedded checkout, remote fonts, account registration, forms, or cookies set by its code. Its theme switch is kept only in the current page, not local storage. It requests its own static files and a local public-acknowledgements JSON file.

The hosting provider still receives ordinary requests and may log IP addresses, timestamps, requested resources, and browser details. No host has been selected for this preview, so no host-specific retention or jurisdiction claim is made. A published host’s policies and an owner-controlled privacy contact must be supplied before launch.

The native application

Peersus does not require a product account. On desktop, it stores the device identity in the system credential store. Android currently stores the identity in a private application file, not a hardware-backed Keystore; uninstalling the app removes that local identity. Settings, pairing/device information and transfer history are kept locally. Local data can contain file names and device details. Use the application’s available management controls and your operating system’s protections; this draft does not promise automatic deletion or an unverified retention period.

Transfers & network metadata

Core device-to-device transfers use encrypted QUIC connections and explicit receive consent. Optional relays can carry encrypted traffic when a direct path cannot be established. Relay operators cannot read the transfer payload but may observe connection metadata, such as network addresses and traffic timing or volume. Direct connectivity can also disclose your network address to the other device. This is not a claim that all traffic stays on a local network or works without internet access.

Clipboard & optional uploads

Clipboard integration is under development and requires explicit sharing and device/plugin permissions. A clipboard can contain passwords or other sensitive content; never assume it is safe to share indiscriminately. Android restricts clipboard access when an app is not focused; automatic always-background synchronization is not promised.

A separate optional cloud-upload plugin is under development. Enabling it means uploading selected files to an external service that may store readable plaintext and apply its own retention and access rules. It is not the core end-to-end encrypted device transfer. Review the provider and URL-sharing risks before enabling it.

The Android WASM upload implementation uses explicit file selection and origin-bound consent. Credentials and provider session secrets remain opaque to the extension; saving an upload credential is optional and uses Android Keystore-backed encryption. Upload HTTPS uses the platform trust store through unmodified rustls-platform-verifier 0.7.1 and its official Android support artifact 0.2.0 (MIT OR Apache-2.0), pinned to upstream revision 1aa691352a5e0c215210dfc9a3c2f2078639dc91. Certificate checks are not bypassed. Automated host/guest tests do not establish device-picker behavior or successful live uploads; those acceptance checks remain pending.

The Android APK carries the licensed first-party upload WASM package. On its first initialization, a missing package is installed through the normal removable-extension manager, without automatically granting file selection or HTTPS access. Existing packages and disabled state are preserved, and a later removal is not reversed on launch. Installing an application or extension does not authorize sending a file to the upload provider.

Voluntary support & payment providers

Only a deliberate click opens Ko-fi. No payment provider code is loaded by this site or support component beforehand. Ko-fi and its payment processors, including Stripe where used, handle payment details under their own policies. The creator may receive transaction records, payer details and messages supplied by the provider; Peersus does not collect your card number. Provider and processing fees may apply.

Tips purchase no product, service, feature, priority, access, or reward. No charitable tax-deductibility is represented. For a payment question, use the transaction’s provider support tools or the creator contact available on the linked Ko-fi page.

Public thanks is a separate choice

The public list starts empty. Only a real supporter’s specifically approved display name may be published, after separate consent. Payment consent is not publication consent. No transaction amounts, email addresses, payer names by default, or payment identifiers are imported. Public recognition is not a purchased entitlement.

To request acknowledgement, correction, or removal, message the creator through the linked Ko-fi page. Publication requests are manually reviewed; no tracking form or webhook imports payment records. Removal affects the maintained page, not copies, caches, or archives held by others.

Dependency maintenance & local patches

This development source includes attributed compatibility backports for network monitoring and Wayland title rendering. The title renderer uses the maintained skrifa font parser instead of the unmaintained ttf-parser chain; network monitoring is being migrated to the maintained netlink dependencies. Manifest-only compatibility patches also migrate the Freya core/components, pulp and rav1e token-pasting dependency to the maintained pastey macro. Direct Linux sleep and desktop-theme watchers are being migrated to zbus 6 (MIT). A local mundy compatibility patch (Apache-2.0) also preserves portal preferences while adopting the maintained bus implementation. A local keyring 3.6.3 patch (MIT OR Apache-2.0, upstream revision 315cbdf6c6a9153d8c9f88b56568f29862d3e39d) removes only the unused asynchronous backend and its legacy dependencies; the existing native backends, synchronous encrypted Secret Service transport and credential lookup/fallback behavior are retained. Source, licenses and modification notices are retained in vendor/keyring, with provenance and removal conditions in PATCHES.md. Thirty-seven targeted identity, relay-token, upload, About/license and locale regressions pass. Actual OS credential access, complete platform-runtime behavior and hosted CI remain unverified. Local AT-SPI, AccessKit and XML signature-validator ports retain accessibility and conformance checks while adopting maintained wire APIs. The desktop UI compiles and retained protocol/signature regressions pass. An isolated private-bus test verifies registry embedding, duplicate registration, cache installation and a cross-connection method call. Full screen-reader/platform behavior remains unverified. The regenerated root lockfile passes the strict local cargo xtask audit gate without vulnerabilities, warnings or suppressions; hosted CI has not been rerun. Original third-party licenses and upstream revisions are retained with the source. A clean dependency audit is not an independent security assessment or proof of runtime compatibility. The strict dependency gate remains in force, and end-to-end platform verification is tracked separately.

Security limitations

No independent security audit has been completed. Encryption cannot protect files on a compromised endpoint, prevent an intended recipient from copying a file, or remove the risks of unsafe plugins and configuration mistakes. Keep backups and independently verify important files.

Before sending a report

Do not post passwords, identity material, private files, payment details, or unredacted logs publicly. A dedicated security-reporting channel and privacy contact have not yet been published; do not invent one or use a public tracker for sensitive disclosures.
